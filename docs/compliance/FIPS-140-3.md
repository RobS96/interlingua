# FIPS 140-3: cryptographic module

FIPS 140-3 validates **cryptographic modules**, through NIST's Cryptographic
Module Validation Program (CMVP). interlingua is not a cryptographic module;
it is an application that uses one. Every cryptographic operation in
interlingua goes through AWS-LC, called through the aws-lc-rs crate.

## Two builds

| Build | Backend | Use |
|---|---|---|
| default (`non-fips` feature) | `aws-lc-sys`: AWS-LC built as an ordinary library | development, and deployments that do not require a validated module |
| `--no-default-features --features fips` | `aws-lc-fips-sys`: the AWS-LC FIPS module build | deployments that require FIPS 140-3 validated cryptography |

`il version` and `il_version()` state which backend a binary uses. CI builds
the FIPS backend and runs the full conformance vectors against it on every
change.

## What makes a deployment "validated"

Building with the `fips` feature is necessary but not sufficient. A
deployment relies on a validated module only when:

1. the AWS-LC FIPS module version that `aws-lc-fips-sys` builds matches a
   version on an **active CMVP certificate** (search the CMVP database for
   "AWS-LC"; check the version and the certificate's status);
2. the **algorithms** used are within that certificate's approved services:
   AES-256-GCM, SHA-384, HKDF and the DRBG have long been; ML-KEM and ML-DSA
   were added to AWS-LC's FIPS module more recently, so confirm that the
   certificate for your version lists them before claiming them as validated;
3. the **operational environment** (processor and operating system) is one
   the certificate covers, or one the vendor affirms under CMVP rules;
4. the module runs in **approved mode**: its power-on self-tests pass, and
   keys are generated inside it (use `SigningKey::generate` and
   `DecapsulationKey::generate`, not seed-derived keys, which exist only for
   test vectors).

interlingua pins the aws-lc-rs version exactly, so the module under a build
changes only through a reviewed dependency update, and the release SBOM
records which version shipped.

## Approved-algorithm use

| Operation | Algorithm | Notes |
|---|---|---|
| Signing | ML-DSA-87 (FIPS 204) | hedged signing (FIPS 204's default) |
| Key establishment | ML-KEM-1024 (FIPS 203) | imported decapsulation keys pass the §7.3 hash check and a pairwise-consistency test |
| Key derivation | HKDF-SHA-384 | SP 800-56C Rev. 2 two-step derivation with a salt |
| Encryption | AES-256-GCM | 96-bit nonce derived per single-use key; never reused |
| Hashing | SHA-384 | |
| Randomness | AWS-LC's DRBG | UUIDv7 random bits and all key generation |

Secret values held by interlingua (derived AEAD keys, shared secrets, exported
private keys) are zeroized when dropped.
