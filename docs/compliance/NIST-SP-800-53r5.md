# NIST SP 800-53 Rev. 5: control mapping

How interlingua supports selected controls of NIST SP 800-53 Revision 5
(*Security and Privacy Controls for Information Systems and Organizations*).
Controls apply to the system that uses interlingua; this table says what the
component contributes.

**Responsibility**: *Provided* = the component implements the control's
mechanism as shipped; *Supported* = the component provides the mechanism and
the operator configures or operates it; *Operator* = outside the component.

## Access and information flow

| Control | Responsibility | How | Evidence |
|---|---|---|---|
| AC-3 Access Enforcement | Supported | a router enforces the policy for every envelope at every hop | `router.rs`; `routing.rsp` |
| AC-4 Information Flow Enforcement | Provided | deny-by-default edges; label checks for source, destination, every edge and every relay | SPEC §8; `routing.rsp` *label-rules* |
| AC-4(1) Object Security and Privacy Attributes | Provided | flow decisions use the label bound to the message (FIPS 199 impacts + compartments) | SPEC §5, §8 |
| AC-4(4) Flow Control of Encrypted Information | Provided | sealed payloads are routed on their signed, cleartext label without decryption; routes and destinations can require sealing | SPEC §7.4, §8 checks 17–18 |
| AC-4(12) Data Type Identifiers | Supported | signed `content_type` in every header, available to host-side filters | SPEC §6 |
| AC-4(17) Domain Authentication | Provided | every message is signed by a key the keyring binds to exactly one source domain; arrivals only over defined edges | SPEC §8 checks 4–7 |
| AC-4(21) Physical or Logical Separation of Information Flows | Supported | compartments and per-edge compartment limits separate flows logically | POLICY.md |
| AC-16 Security and Privacy Attributes | Provided | labels are bound to the message under its signature and checked at each hop | SPEC §5, §7.3 |

## Audit and accountability

| Control | Responsibility | How | Evidence |
|---|---|---|---|
| AU-2 Event Logging | Provided | every routing decision, accepted or rejected, is an event | SPEC §8.3 |
| AU-3 Content of Audit Records | Provided | what (verdict, reason), when (time), where (node), source and destination, outcome, message identity, envelope hash, authenticity state | SPEC §8.3 |
| AU-8 Time Stamps | Supported | records carry the router's time; the operator supplies synchronized time | OPERATIONS.md §4 |
| AU-9 Protection of Audit Information | Supported | records are hash-chained; operator ships them to protected storage | `audit.rs`; OPERATIONS.md §5 |
| AU-9(3) Cryptographic Protection | Provided | SHA-384 chain detects modification, insertion, deletion, reordering | `il audit-verify`; audit tests |
| AU-10 Non-repudiation | Provided | ML-DSA-87 signatures bind each message to its source domain's key | SPEC §7.3 |
| AU-12 Audit Record Generation | Provided | generated by the component for every decision | `Router::route` |

## Identification and authentication

| Control | Responsibility | How | Evidence |
|---|---|---|---|
| IA-3 Device Identification and Authentication | Supported | each domain (and so each router host) is identified by its signing key | SPEC §7.2 |
| IA-5 Authenticator Management | Supported | key generation, bundles, rotation guidance; key storage is the operator's | OPERATIONS.md §1–3 |
| IA-7 Cryptographic Module Authentication | Supported | build against the AWS-LC FIPS module and operate it in approved mode | FIPS-140-3.md |

## System and communications protection

| Control | Responsibility | How | Evidence |
|---|---|---|---|
| SC-5 Denial-of-Service Protection | Provided | bounded decoders, per-source rate limits, bounded fail-closed replay cache | SPEC §3, §8.2; `routing.rsp` *rate-limit* |
| SC-7 Boundary Protection | Supported | a router at each domain boundary mediates every flow | ARCHITECTURE.md §2 |
| SC-8 Transmission Confidentiality and Integrity | Provided | end-to-end signatures; sealing for confidentiality | SPEC §7 |
| SC-8(1) Cryptographic Protection | Provided | ML-DSA-87, ML-KEM-1024, AES-256-GCM | CNSA-2.0.md |
| SC-12 Cryptographic Key Establishment and Management | Supported | ML-KEM-1024 per message; key lifecycle guidance | OPERATIONS.md §3 |
| SC-13 Cryptographic Protection | Provided | CNSA 2.0 algorithms only; FIPS module option | CNSA-2.0.md, FIPS-140-3.md |
| SC-16 Transmission of Security and Privacy Attributes | Provided | the label travels with the message, inside the signed header | SPEC §6 |
| SC-16(1) Integrity Verification | Provided | label integrity is verified by the signature at every hop | SPEC §8 checks 5–7 |
| SC-28 Protection of Information at Rest | Supported | sealed payloads stay encrypted in queues and stores until the destination opens them | SPEC §7.4 |

## System and information integrity

| Control | Responsibility | How | Evidence |
|---|---|---|---|
| SI-7 Software, Firmware, and Information Integrity | Provided (information) | message integrity verified before any use; release integrity via provenance | SPEC §7.3; SUPPLY-CHAIN.md |
| SI-10 Information Input Validation | Provided | strict decoding with bounds; identifiers, labels and policies validated | `cbor.rsp`, `label.rsp`; fuzz targets |
| SI-11 Error Handling | Provided | stable error identifiers; no secrets in errors; panics contained at the ABI | SPEC §9; `interlingua-ffi` |
| SI-16 Memory Protection | Provided | memory-safe Rust core; `unsafe` confined and justified | MEMORY-SAFETY-ROADMAP.md |

## Not addressed by the component

Contingency planning, personnel security, physical protection, incident
response organisation, continuous monitoring programmes, and penetration
testing of a deployed system (CA-8) are the system owner's.
